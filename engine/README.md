# engine — `.tzs` 表单引擎（C#）

`tt dev tzs` 背后那个进程：它读写设计器的 `.tzs` 表单包。

**它不实现 `.tzs` 格式。** 它加载**设计器自己的程序集**，布局属性走设计器自己的索引器、
`.tsd` 由设计器从模型重算 —— 格式那部分是设计器自己在算。我们这部分只是驱动层。

## 两层源码，依赖单向

| 层 | 源 | 产物 | 职责 |
|---|---|---|---|
| 纯文本 / 容器层 | `src/*.cs` | `TzsCli.dll` | 记录重建、表单写出、包重打 —— **不反射、不碰界面框架** |
| 反射管线层 | `src/Designer/**`（动词实现体在 `Fns/`） | `TzsCli.Designer.dll` | 引导、反射调用、会话、传输（命名管道）、函数表、各动词实现 |

`TzsCli.Designer.dll` 引 `TzsCli.dll`，反过来什么都不引（否则同类型出现两份）。
构建时编完第一个库立刻校验它的引用集：一旦出现设计器程序集或撤销栈组件，即判定分层被破坏
并让构建失败。

`test/*.cs` 是十几个独立程序：两个主程序（引擎服务端与引擎自带的客户端）+ 一批探测程序
（往返、重打、探针…）。它们**只供开发**，不进发行包，也不用测试框架跑。

## 设计器程序集随仓库走

`designer/` 里是设计器的 28 个程序集（约 10.5 MB），**入库、随发行包分发**：

- **编译期**只引用其中一个（JSON 库）。
- **运行期**用 `Assembly.LoadFrom` 加载其余全部；查找顺序固定两条，**没有第三条兜底**：
  `TZSCLI_INSTALL`（覆盖用）→ **引擎自己目录下的 `designer/`**。
- 构建脚本编完会把仓库里那份采到产物目录，所以引擎从源码树直接能跑、**不需要任何环境变量** ——
  与发行包的布局是同一个。

为什么入库而不是让用户自己装：同一份 `tt` 在两台机器上，如果设计器目录来自各自的配置，
跑的就是两版设计器 —— 同一个包行为不同，而报错里看不出来。跟着仓库/包走之后，
"运行环境一致"是**分发这件事本身**保证的。

**换设计器版本 = 换 `designer/` 下的文件并提交**，是一次可 review 的改动。

## 进发行包的是三件加一个目录

`tzs-server.exe` + 两个库 + `designer/`。引擎自带的那个客户端**不进包** ——
对外只有 `tt` 一个入口，两个客户端就是两套命令面与两套退出码；它仍照编，
引擎侧的验收程序用它。

## 为什么单独构建（不挂到后端构建上）

1. **它不属于 Go 的构建链**：用系统自带的 .NET Framework 4.0 编译器（C# 5）引 GAC 里的
   界面框架程序集，没有工程文件、不用 MSBuild。打包脚本只**采集**产物，不构建它。
2. **重编会让在跑的守护进程变成孤儿**：守护进程的管道名包含本程序集的标识，每次重编都变。
   客户端因此**永远连不到**跑着陈旧字节的守护进程（这是刻意的，否则会与旧行为对话而看不出来）；
   代价是每个上一版构建起的守护进程再也停不掉，由 `tt dev tzs reap` 收。
3. **设计器程序集跟着产物走**（见上），所以引擎不需要任何环境变量。

**只在引擎真的改了时才重编。**

## 一条现状约束：函数面覆盖目前是空的

引擎的语料回归驱动的是 8–10 个函数，是**回归网，不是函数面的覆盖网**。
把全部写函数跑在一个长驻进程里的脚本（`gate-w3-fns.py`）**跑不起来** —— 它在运行时从路径加载
`gate-w3.py`，而那份不在仓库里。于是脚本里那批"每个写函数分组至少一条、必须以契约码被拒
且零字节改动"的负向对照也**没有在跑**。**函数面覆盖目前是空的**，要补得在 Go 侧补。

## 构建与判据

```bash
cd engine && ./build.sh          # → engine/out/，并把 designer/ 采进去
./tt.exe dev tzs doctor          # 引擎 exe / 设计器 / 工作区 / 管道名 / 守护进程，五面自检
cd engine && ./build.sh TzsCli.Designer   # 只编一个
OUT=<dir> ./build.sh             # 换落点
TZSCLI_INSTALL=<别的设计器目录> ./build.sh  # 用别的设计器版本覆盖仓库里那份
```
