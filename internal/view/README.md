# internal/view — 窗口与图像

**做什么**：按 pid 枚举顶层窗口、抓某个窗口的**真图**、裁掉不该有的东西、过一遍交付体检、
在图上画标注框（落点由调用方从协议里算出来，本层不猜坐标）。

**不做什么**：

- 不碰键鼠、不改窗口样式、不置顶（那是驱动层的事，本层不提供这些入口）；
- 不自己找"哪个是作业窗口" —— 窗口与作业的对应关系由上层（`tt fep` 的会话与 AUI）给出；
- 不做缩放：合成一律用 Go 的 `image/draw` 逐像素画。PowerShell/GDI+ 的 `DrawImage`
  会按 DPI 比自动缩放（96/120 → 画布右侧 20% 变黑），实测踩过。

## 抓图后端与理由（都在真机上量过）

| 后端 | 结论 |
|---|---|
| `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` | **首选**：不受遮挡、含标题栏与滚动条、不透出背后窗口的像素 |
| `GetDC(hwnd)` 客户区 | 降级：缺标题栏/滚动条 |
| `GetWindowDC` | **弹窗不能用**：会透出背后窗口的像素（实测看到过电子书网页） |
| 屏幕抓取 | 所见即所得，但**受遮挡**（实测抓到过两个窗口完全重合） |

漏掉 `PW_RENDERFULLCONTENT` 会得到一张全白图 —— 当年"QT 抓不了"的错误结论就是这么来的。

## 两条必须记住的规矩（各踩过一次）

1. **DPI 感知必须在任何 GDI 调用之前声明**。没声明时进程看的是虚拟桌面坐标
   （1920×1200 变成 1536×960），窗口右侧被剪 8~14px、左侧出现 7px 黑边 —— 而图看起来
   仍然"像一张正常的截图"。代码里用 `ensureDPI()`（`sync.Once`）保证顺序。
2. **枚举窗口只按 pid**（+可见+尺寸），绝不按类名：作业窗口与开窗的窗口类不同
   （`Qt5QWindowToolSaveBits` ≠ `Qt5QWindowIcon`），按类名过滤会漏掉开窗。
   枚举是同步跨进程调用，所以带超时（`ListTimeout`）：目标线程忙时不能让命令一起卡住。

## 阴影裁切

DWM 给窗口留的阴影区在 PrintWindow 里是**纯黑**（实测左/右/下各 9px，窗口矩形外扩 -9,-9）。
裁切的坑：**左右列的检测必须跳过标题栏那几行**（标题栏是亮的 243,243,243），否则标题栏
会让整列判成"非黑"，一列都裁不掉。

## 交付体检（`Check`）

抓图是"看起来对"最容易骗人的一步。每次抓完自动过：

1. 几乎只有一两种颜色 → 全白/全空图（多半漏了 `PW_RENDERFULLCONTENT`）；
2. 右端出现纯黑列 → 没裁阴影，或抓图区域被剪（DPI 感知没声明）；
3. 尺寸异常。

体检不过：`tt view shot` 退 **4**，并把问题打出来。

## 判据

- `go test ./internal/view/`：阴影裁切（含"标题栏行不参与左右判定"）、无黑边时不乱裁、
  体检能指出全白图与黑列、窗口筛选与按名查找；
- 真机：`tt view shot --pid <pid>` 抓一个真实窗口 → 图片尺寸 = 窗口矩形减两侧阴影、
  颜色数正常、体检零问题（实测：1938×1158 的窗口 → 1920×1140，363 色）。

## 协议坐标 → 图像坐标（`annotate.go`）：机制已就位，一个测量待真机

`Derive` 从**参照物**推出比例与偏移（不写死比例：换主题/换机器就全错，而且错得很像对的），
推出来的东西离谱就**报错**；`RegionVerdict` / `GateFields` 是像素级可见性门
（计划 §2.12）：说明里点名的栏位必须在那一帧里真的画出来了。

**离线卡在一个测量上**（不猜，留真机）：真实 AUI 的几何属性**单位不统一** ——
实测同一屏里 `ButtonEdit 272 {width "8"} {posY "2"}`（**字符格**）与
`Window 178 {width "1912"}`（**像素**）并存。所以"哪个对象是客户区、哪个坐标系对哪个"，
离线推不出来：拿窗口当参照物会推出荒唐的纵向下移（实测 1038px），拿并集也被像素对象带偏。

因此当前行为是**拒画**：`tt view marks` 在映射推不出来时退 **4** 并说明理由，
绝不画一个"看着像"的框。下一次真机联调要做的测量：抓一帧 GDC、把已知栏位
（如「客户编号」）的框叠上去，用眼睛确认落点 —— 那一步会定下单位与客户区上沿，
之后映射才有依据。

## 坐标校准：靠实测，不靠推断（`calibrate.go`）

真机上量到的两组数（同一列 `posX=15` 在第 1、2 行的文字左端都是 **x=526**；两行 y 差
**32px = 1 格**）说明：比例是存在的，但**静态推不出来** —— AUI 里累积着多个画面的对象，
且几何单位混用。所以映射通过一次**实测校准**得到：

1. 往两个已知栏位各写一个值（`tt fep` 注入）；
2. 各拍一张图，取**像素差**（`DiffBox`）—— 变化的那些像素就是那个栏位在屏幕上的真实位置；
3. `SolveMapping` 由两个锚点解出 (格宽, 格高, 原点)，残差大就报出来（说明两次取值不是同一列/行）。

判据：`TestSolveMappingFromTwoSamples` 用的就是真机那一组数；预测出的
`Map(Box{15,2,10,1})` 必须落在实测锚点 (526,215) 上。

## `tt view calibrate`：把校准做成一等公民（已离线验证到像素级）

```
tt view calibrate            # 自动挑 3 个可写栏位 → 各注入一个值 → 拍前后两张 → 取像素差 → 解映射 → 存 JSON
tt view calibrate --dry-run  # 只列候选与它们的协议坐标，一个字节都不发
tt view marks --png job.png --field 客户编号 --field 订购单号   # 用存下的校准把框画准
```

样本的体检（不信任任何一条证据）：差异框超过 600px 宽 / 120px 高 → 判为"那一枪引起了
别的重绘"，该样本弃用；两个样本互相矛盾（残差 > 6px）→ **报错**，绝不出勉强拟合的映射。
`marks` 在没有校准时**拒画**（退 4）并指路去跑 calibrate。

**离线验证到像素级**（用真机会话的 AUI + 那次真机测量得到的校准）：

```
参照物 实测校准 → 比例 7.000，客户区上沿 151px
1. 客户编号 ButtonEdit#272  图内 70x32+526+215     ← 当时实测文字就在 526,215
2. 订单单号 ButtonEdit#260  图内 147x32+505+215    ← posX=12 → 421+12×7 = 505
```

两个实现细节都是真机逼出来的：同一屏会累积多个画面的**同名对象**（查询画面那份停在
(0,0)，是"没定位"的副本，必须排除）；`height` 在真实 AUI 里常常缺省（按 1 格算）。

## 真机验收（2026-10-11）：标注框落在栏位上，可见性门抓出"不在这一帧"的栏位

```
tt view shot --out job.png                       → 1920x1149，651 色，体检零问题
tt view marks --png job.png --calibration <实测> --field 客户编号 --field 订单日期 --field 母项目号
  1. 客户编号 ButtonEdit#272  图内 70x32+526+215   ✔ 通过（框落在栏位左沿）
  2. 订单日期 DateEdit#269    图内 70x32+526+183   ✔ 通过（框压在 2026/10/11 上）
  3. 母项目号 ButtonEdit#326  图内 126x32+505+311  ✘ 门判"这块区域是纯色 —— 该栏位在那一帧里没画出来"
```

第 3 条是**门真正的价值**：母项目号在另一个标签页上，这一帧根本没有它 ——
上一版手册里"标题点名了一个画面里看不见的栏位"就是这么发生的。现在它被抓住并说明理由。

自动取样本还有一处不稳（右对齐栏位：文字左端 ≠ 栏位左沿；邻居重绘会污染差异框），
所以 calibrate 的规矩是：**多取样本 + 两两拟合 + 用外面的样本查残差**，
解不出合理比例（2–40 / 8–64）就报错拒画；显式 `--field` 指定总是可用的退路。

## 成品：v12 手册（真图 + 实测校准 + 可见性门）

```
%APPDATA%\tt\fep\T100-操作手册-v12.pptx     （7 页，含导图自查）
%APPDATA%\tt\fep\img-v12\                   （4 张真图：录入画面 / 表头标注 / 客户编号 / 门失败的例子）
%APPDATA%\tt\fep\calibration.json           （实测校准：格宽 7.0、格高 32、原点 421,151）
```

这一版与以往三处不同，都是这一轮做出来的：① 图是 `tt view shot` 抓的**真图**
（PrintWindow + PW_RENDERFULLCONTENT + 裁阴影 + 交付体检）；② 标注框的换算来自**实测校准**
（`tt view calibrate` 的思路：注入 + 像素差），不是推断；③ 每个被点名的栏位都过
**可见性门**（那一页里「母项目号」就因为它在另一个标签页上没画出来而被门抓住）。

**刻意保留的边界**（写进手册里，不含糊）：

1. **明细网格的格子不画框**：协议里那些格子没有坐标（`geom=0,0`），画框只能是猜 ——
   宁可标注清楚"这一帧里没有坐标"，也不猜。
2. **合成的"点开窗"还不稳**：实机点 `ButtonEdit{controlp}` 只回了 ACK（+79 字节），
   窗口没开；真人是用双开/键盘触发的。那类步骤要么由人亲手点再录，要么等把事件上下文补全。
3. 手册只写**跑过且有协议证据**的步骤。

## `tt view measure`：给"协议里没有坐标的东西"量位置（真机已验证）

明细网格的格子就是这样：实测 `TableColumn` 与运行时的 `Value` **都没有 `posX/posY`**
（带几何的 Value 对象数为 0）—— 没有坐标就不能推，只能量：

```
tt view measure --target 客户编号 --value 24680 --name "客户编号(实测)"
  → 已量到区域 "客户编号(实测)"：97,178,478,50（变化 384 像素）
tt view marks --png job.png --region "客户编号(实测)" --out annotated.png
```

量到的矩形连同**来源与时间**一起存进 `regions.json`；`marks --region` 直接用它出框
（绕开坐标映射），出框时会标成"实测区域"而不是"协议坐标"。

两条用真机换来的规矩（都写成了拒绝理由）：

- **值必须与当前值不同**：往已经是 `2026/10/11` 的日期栏位再写同一个值，量到 `1x23` 的
  细条 —— 太薄/太扁的差异框一律拒收（不是栏位边界，是光标闪动之类）。
- **邻居重绘会把框撑大**：改「客户编号」会让运行期把旁边的「交易对象简称」一起重画，
  量到的框跨两行（`97,178,478,50`）。这种框照实存，但档案里注明"可能含邻居重绘，
  框偏大" —— 用的人必须知道它不是一个栏位的边界。

## 明细网格格子：找到它、量出它的完整方法（真机对照出来）

网格格子在协议里**既没有坐标也没有名字**（实测：带几何的 Value 为 0；格子的名字解析为
`(未解析)`）。所以流程是"**按值找 → 按 id 量**"：

```
tt fep ui find --value "1,000.000"        → #3009 Value（未解析）value="1,000.000"   ← 就是订购量那个格子
tt view measure --target '#3009' --value 2000 --name "明细订购量(第1行)"
tt view marks --png job.png --region "明细订购量(第1行)" --out annotated.png
```

三条真机教训：

1. **`measure` 要求目标在"当前可见的这一帧"里**：不在就得到"写了值但屏幕没有变化"
   （工具如实报出这两种可能，不会假装成功）。
2. **已保存/已审核的单子整单只读**：真人那一轮把单存成了 `Y:已审核`，之后对格子的任何输入
   都不再改变屏幕 —— 量坐标必须在**编辑中的新单**上做。
3. 网格格子的 id 每轮不同，所以**按值找**是唯一稳定的入口（`ui find --value`）。
