# internal/dict/db — 本地镜像与查询接口

两件事：**本地 SQLite 镜像**的读取实现，以及全部查询命令依赖的那个**接口定义**。

## 一个接口，两个实现

`Source` 是 ERP 字典"语义查询"的统一接口：每个查询命令只依赖它，不关心数据来自本地还是远程。
接口方法本身就是表的清单 —— 表字典、程序与作业字典、子程序与元件、校验带值、字段规格、
系统分类码、可复用开窗、系统消息、参数定义。

| 实现 | 在哪 |
|---|---|
| `*DB`（本地 SQLite 镜像） | 本包 |
| `*live.Live`（远程直查） | [../live/README.md](../live/README.md) |

**两边的语义必须一致**：同一组查询方法、同一批返回结构、同一套表与连接方式。
这是"命令层不区分数据源"能成立的前提。

## 本地镜像

- 连接壳用纯 Go 的 SQLite 驱动（无 cgo），所以构建不需要 C 工具链。
- 每个查询命令一个文件，按**数据族**组织（表字典、校验带值、分类码、规格、开窗、消息、
  参数定义、程序与作业…），每族读它那几张表。
- 未收录的表/程序返回"没有这条"（而不是空结构），调用方据此给出"查无结果"。

## 提示的另一半：帮助里的"本地数据齐不齐"

各命令的帮助末尾会提示"这个命令依赖哪个数据族、本地齐不齐"。那个映射与数据族清单同源 ——
所以加一条命令或改一族范围时，**改数据族定义那一处就够**。

## 判据

```bash
go test ./internal/dict/db -count=1
```

覆盖：消息查询的各种条件组合（精确码 / 文本 / 程序名 / 类型状态 / 无条件）与语言选择。
各族的其它查询由命令层用例覆盖。

## 改动影响面

| 改什么 | 会波及 |
|---|---|
| `Source` 接口 | 两个实现都要跟着改；命令层全部依赖它 |
| 表名或 JOIN | 本地镜像与远程直查**必须同步改**，否则两个数据源给出不同结果 |
| 数据族清单 | 同步范围、覆盖状态、帮助提示三处同源，改一处即可 |
| 本地库文件位置 | 由配置的同步目标与命令行的库参数决定（缺省是当前目录下的本地库） |
