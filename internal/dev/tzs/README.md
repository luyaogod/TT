# internal/dev/tzs — `.tzs` 引擎客户端

`.tzs` / `.tzv` 表单包的读写，由**设计器自己的引擎**（C# 外部进程 `tzs-server.exe`）执行；
本包是它的 Go 客户端与守护进程管理。

**它只做两件事，都不做业务判断**：

| 文件 | 职责 |
|---|---|
| `client.go` | 一次调用：连 → 发 → 收 → 把结果归类成类型化错误 |
| `server.go` | 守护进程生命周期：起进程 / 就绪握手 / 状态文件 / 停止 / 收孤儿 |
| `form42f_check.go` | **静态**校验：`.42f`（应然）↔ tzs 生成物（实然）—— 不连引擎，见下文 |

**依赖面刻意窄**：只 import [config](../../config/README.md)（状态文件落点）与
[winproc](../../winproc/README.md)（起 / 判活 / 杀）加标准库；`form42f_check.go` 另外 import
[form42f](../../form42f) 的**纯解析器** `ParseForm42F`（`.42f` 的解析只有一份，本包不重写它）
—— 方向是 `dev/tzs → form42f`，而 `form42f` 不 import `dev/*`，所以不成环。
它**不 import `internal/cli/dev`** —— 那边 import 它，反过来就成环。命令层（动词分发、退出码、文案）住在
[cli](../../cli/dev/README.md)，本包只提供退出码映射这类纯函数供它调用。

## 三条纪律

**一、管道名问引擎，不自己算、不缓存。**
名字里混了 `TzsCli.Designer.dll` 的 MVID，每次重编都变。自己重算（或跨调用缓存）算错任何一半
都是**静默失败**：客户端连到一个没人监听的管道、判定"没有守护进程"、起一个新的、还是连不上
（新起的那个监听的是另一个名字），最后报出来的是"冷启动未就绪" —— 与真实原因毫无关系。
所以只用引擎的 `--pipe-name` 开关问一次，代价是几十毫秒（这个开关不 Boot）。

**二、工作区绝不留缺省。**
引擎的内置默认工作区是一个**真实客户目录**。留空就等于拿客户的表单当草稿纸，所以工作区解析
不出来时一律拒绝（退出码 2），**绝不拉起守护进程**。工作区**按环境**配
（`hosts.sshs[].workspace`，即设置页「站点管理 → 环境 → 工作区目录」）：一台机器对着几个
客户就有几个工作区，放在机器级只会让“切了环境、引擎还开在别的客户的目录上”有机会发生。

**三、请求一旦上线绝不重试。**
协议没有幂等键，而这些函数都在改设计器内存里的模型；中途失败时重试是在赌"上一次写进去了没有"。
两种失败要分开对待：

| 现象 | 判定 | 含义 |
|---|---|---|
| 先来一帧致命错误（加载超时）然后 EOF | `E_FATAL_LOAD_TIMEOUT` | 确定性的失败，不重试 |
| 一帧都没有的 EOF | `E_SERVER_DIED` | 连接断了；**下一个**命令可以重新拉起守护进程 |

## 帧

**一行 JSON + 一个换行，UTF-8 无 BOM**，两个方向共用同一条规则，但容错面相反：

- **出方向**只发换行，且**拒绝**帧里出现裸的回车/换行。理由不是洁癖：一个裸换行会把一帧劈成
  两帧，对端在下一次请求上读到上一帧的尾巴，之后每一帧都错位一格 —— 症状是"参数明明对，引擎
  却报参数错或未知函数"。我们的帧全部由 JSON 编码器产出（换行必被转义），所以这条闸门只会
  逮住手搓的帧。
- **入方向**容忍行尾的回车与行首的 BOM。这两个容错不是可选项：标准输入输出模式下的日志/诊断
  可能混到同一条流上，而 BOM 是记事本一类工具的默认输出。
- **行长上限 8 MiB**（双向）。**不要用默认 64 KiB 上限的扫描器**：`form_tree` 在大表单上
  一次就几十万字节，那会以"token too long"终止，读起来像表单坏了。

**不是合法帧的三种情况一律归传输失败**（退出码 5），绝不合成一个看起来像业务错误的应答。
而几处**根本到不了引擎**的失败（连不上、本地参数错、manifest 拉不到）会**合成一帧**
（`SyntheticFailure`），形状与引擎帧完全一致 —— 消费方不必分辨是谁发的。

## 参数：manifest 是唯一权威

命令面只接受**一种**参数写法：`--args '<JSON 对象>'` / `--args-file <文件>`。没有
`--<参数> <值>` 那种写法 —— 参数的名字与类型是**运行时**从引擎的 manifest 来的，
照它为每个动词手写一遍就是几十处会跟引擎漂移的代码。

**绝不在 Go 侧抄第二份参数表。** 本包只做三件事：解 manifest、按名字查表、渲染帮助。
本地只做**语法**层校验（未知动词 / 未知参数 / 缺必填 / 类型 / 枚举静态取值 / 数组元素类型），
语义留给引擎。有三处**本地不拦**：

| 参数 | 为什么拦不了 |
|---|---|
| `kind` | 合法集不在 manifest 里（七种） |
| `attr` | 合法集要从**活着的模型**里取 |
| `add_action` 的 `type` | 是每张表单自己的词表 |

拦下来会让一个引擎本会接受的调用**永远到不了引擎**，而越界拦截是无声发生的（写错了不会有
任何测试失败）。引擎拒绝它们的退出码与本地拦下来一模一样，所以放过不会让报错变晚或变差。

**与引擎自带客户端的一处有意差异**：位置参数与未知开关一律**当场报错**，而引擎那个客户端会
"忽略非选项参数"并继续 —— 无声忽略正是要治的病（打错的参数与一次合法调用在结果上无法区分）。

## 守护进程

**就绪握手**：每 250 ms 试连一次，单次连接超时 300 ms，**连得上就算就绪**（不发任何帧），
预算 60 s。为什么连上就算：管道是引导完成**之后**才创建的，且服务端实例只允许一个，
所以"连上"本身就证明了"引导做完且服务端正等在这里"。**Go 侧不该在传输层写死一个业务函数名。**

**不与 [../../cli/debug](../../cli/debug/README.md) 的后台服务复用**：形状相似但三条前提相反
（我们探命名管道且名字要问引擎 / 状态文件按工作区多条 / 失败还要分有没有致命帧）。
相同的只有"起子进程、判活、杀"三件纯进程原语，那部分已经抽在 `internal/winproc`。

**停止与收孤儿**：`stop` 不带参数就可用（按状态文件找本工作区的守护进程）；
`reap` 收"重编引擎之后再也停不掉"的孤儿。**问不到当前管道名时（引擎 exe 没了/坏了）一个都不动** ——
那时没法把孤儿与现役区分开，猜错就是杀掉一个正在被别的客户端使用的守护进程。

## 状态文件 `.tt-tzs.json`

**必须与 `.tt-serve.json` 分开。** 服务那份要求 URL 非空；一旦混进一条没有 URL 的守护进程记录，
`tt serve` 的单实例判断会当场认为状态文件损坏（于是再拉一个服务抢端口），而 `tt serve --stop`
会拿着引擎的进程号去杀 —— 指错人是这类文件最坏的失败方式：它看起来"成功了"。

结构按工作区键控（一个工作区同时只有一个守护进程），**键是小写的工作区原串，刻意不做路径归一**：
小写是引擎自己的口径（它拿小写串去算管道名），不做清理是因为那会**改变身份** ——
`D:\ws` 与 `D:\ws\` 是两个不同的管道名、两个不同的守护进程，归一成一条会互相覆盖，
`reap` 从此看不到其中一个。

## `doctor`：把"为什么用不了"一次答完

这条链上有五个独立的失败面，而它们的**现象几乎一样**（都是"连不上"），照着现象排查会一路走错：

| 失败面 | 表面现象 |
|---|---|
| 引擎 exe 路径不对 | 问不到管道名 |
| 设计器没装/版本不对 | 冷启动未就绪（真正的错误藏在守护进程日志里） |
| 工作区没配/配错 | 没有守护进程在监听（名字按工作区算） |
| 有陈旧构建留下的孤儿 | 一切正常，只是在吃内存 |
| 状态文件损坏 | 已被静默挪走，但用户该知道 |

`doctor` 把它们分开答，每条给出"在哪看到的"和"怎么办"。它不引导任何东西（只跑两个不引导的
开关），所以可以随便跑。

## `formcheck`：应然 vs 实然 的**静态**校验（M3）

一张表单有两个来源，本文件负责把它们对起来：

| 侧 | 是什么 | 出处 |
|---|---|---|
| **应然** | `.42f`（编译后的表单，明文 XML）—— **声明期权威** | `form42f.ParseForm42F`（切片 A 已交付，509/509 对齐） |
| **实然** | tzs 生成物里的表单描述：`.tzs`/`.tzv` 包内的 `.4fd`（或摊在工作区里的明文 `.4fd`） | 本文件的 `ParseTzsForm4FD` |

**为什么挑 `.4fd` 当"实然"**：它和 `.42f` **属性同名同义**（`colName` / `fieldId` / `widget` /
`noEntry` / `required` / `notNull`），所以比对不需要任何换算表。包里的 `.tsd` **不用** ——
它**没有** `fieldId`，做不了编号比对。

四组差异（顺序固定，`RuleOrder`）——每条都给 `colName`、两侧值、**为什么**：

| 组 | 判据 | 算什么 |
|---|---|---|
| **存在性** | tzs 声明的 `colName` 在 `.42f` 里没有 | 确定差异 |
| **编号** | 两侧都有但 `fieldId` 不同 | **基数感知**（契约 A37）：先看全部唯一配对的差值（tzs − `.42f`）——**恒差一个非零常数** ⇒ 一条**聚合说明**（`Notes`），不逐条报；差值**散开**（或只有 1 对——那时"恒定"恒真，谈不上分布）⇒ 逐条报"编号不同"，理由里点明"**可能是另一张表单/版本不同**"（B5）。`.4fd` 的 `fieldId` 每次保存会全量重排 ⇒ 是"可疑"不是"错误" |
| **可写性** | `noEntry` / `required` / `notNull` **同属性**对齐 | 同属性反向才可能是确定差异，方向写死：**`.42f` = 应然、tzs = 实然**，并翻成人话（"可输入/不可输入"、"必填/非必填"、"栏位非空/允许为空"）。**跨属性组合**（`notNull=true` 而 `required=false`）只进"未判定"（A38，疑似编译器把 NOT NULL 归一成必填） |
| **控件族** | `Widget` 与 tzs 侧控件**确定**不等价 | 确定差异（两侧都是已知控件名） |

> **为什么"编号"必须基数感知**（2026-10-17 真实配对把旧规则打穿）：`aimm200_wf` 两侧各 171 条、配对 93 对，
> `.42f` 的 `fieldId` 是 0..170（0 基）、`.4fd` 的是 1..171（1 基），按文档顺序逐行对齐 **171 行恒差 +1**
> （直方图只有 `+1`）。旧规则裸比两侧 `fieldId` ⇒ **86/86 唯一配对全部命中**，对"是不是另一张表单"
> 零分辨力。所以判据改成"差值是否恒定"，**不猜**哪一侧是 0 基（措辞只陈述"恒差 +1"）。
>
> 聚合说明**不是差异**：`Consistent()` 不看它（退出码不受影响），但它**必须印出来** ——
> "降级成说明"与"删掉"是两件事（`【说明】` 段 + `Notes` + `--json` 的 `notes`）。

**"未判定"是这个功能的一半**（契约 A15/A18：启发式不得参与判定）。四种情况进未判定，
**不计入错误**、`Consistent()` 仍为 true，但**必须打印**：

1. 控件名不在 `widgetCanonTable` 里（只收两侧**实测见过**的 16 个名字；`FFLabel≡Label≡StaticText`、
   `FFImage≡Image` 这两族做归并，其余不许跨名合并 —— `Edit` 与 `TextEdit`（单行/多行）、
   `Edit` 与 `ButtonEdit`（有无开窗按钮）是**不同**控件，要如实报）；
2. 某一侧**没带控件类型**（`.42f` 的 `TableColumn`/`PhantomColumn` 一类会是空）；
3. `colName` **重名**（两侧任一）⇒ 编号/可写性/控件族**都不判**，只留一条说明（重名是正常形状：
   实测 `aapt300.4fd` 里 `chr80` 出现 4 次）。同理，tzs 侧**没声明**某个布尔属性时也不比 ——
   "未声明"不等于"声明为 false"；
4. **跨属性组合**（A38）：`notNull=true` 而 `required=false`（或反向）出现在任一侧 ⇒ "可写性"记未判定，
   说明里写"疑似编译器把 NOT NULL 归一成必填，非设计变更"。真实配对里那 4 条 `CheckBox`
   （`imaa036`/`imaa037`/`imaa038`/`imac002`：两侧 `notNull` 一致、只有 `required` 反向）就是它，
   **一份快照**排除不了"导出后又改必填"，所以措辞一律"疑似"、**不许**写成定论。

**实测基线**（2026-10-17，本机）：

- 真样本 `t100/axmt500_wf.42f`：**563 条**全部配成对、差异 0 条、未判定 **34** 条
  （`Aggregate×22` + `PhantomEdit×12` —— 这两个名字**刻意**留在表外：它们不是录入控件，
  猜一个族就等于给"看起来对"开门）；
- 仓库自带语料 `testdata/tzs-mini/ws/aapp320(c).tzs`：包内 `.4fd` 有 **56** 条带 `fieldId` 的元素，
  其中 **45** 条有 `colName`（其余是 `NON_DATABASE` 占位控件）。
  `<RecordField>` **不算字段**（它带的是 `fieldIdRef`；算进去每张字段会被数两遍）。

**入口**（都在本包，命令层只转发）：

```go
ParseTzsForm4FD(prog, text string) (*TzsForm, error)   // 纯函数：不 IO、不 panic
ReadTzsForm4FD(path string) (*TzsForm, error)          // 明文 .4fd
ReadTzsFormPackage(pkgPath string) (*TzsForm, error)   // .tzs/.tzv（zip；只解那一个 .4fd 条目）
CheckForm42F(want *form42f.F42Form, got *TzsForm) *FormCheck
```

`FormCheck` 的读法：`Diffs()`（**确定**差异）/ `Undecided()` / `Group(rule)` / `NoteFor(rule)`（**聚合说明**）/
`Consistent()` / `String()`（人读的分组清单，**刻意不给百分比**）/ `JSONReport()`。

`JSONReport()` 的键（改了要同步调用方与
[cli](../../cli/dev/tzs/README.md)）：`ok` / `form` / `declared_name_42f` / `prog_tzs` /
`f42_fields` / `tzs_fields` / `tzs_unnamed` / `pairs` / `diff_count` / `undecided_count` /
`note_count` / `groups{exist,fieldid,writable,widget}` / `notes` / `undecided` / `f42_only`。

`notes` 是**聚合说明**（A37）：`{rule, text, pairs, cols}`。它不是差异（`ok` 不看它），但**必须**输出 ——
不然"86 条降级成 1 条说明"就会退化成"86 条消失"。

`f42_only` 是**信息**（只在 `.42f` 里有、tzs 侧没声明）—— 不算差异：一个包可以只维护表单的一部分。

**不做的**：不判 `Tag`（`.42f` 的 `TableColumn`/`PhantomColumn` 与 `.4fd` 的元素名不是同一套词表，
实测 `.4fd` 里是 `<Phantom>`）；不判几何/`tabIndex`（布局归设计器）；不查字典、不猜中文名；
**不猜**"两个不同控件名是不是同一件事"。

**已知局限**：`.4fd` 与 `.42f` 的 `fieldId` 是不是**同一物** —— **2026-10-17 用第一份真实配对把这条
答了：不是同一物，差一个下标基数**（见下一节）。所以"编号"这条**先看整体基数差**（恒差 ⇒ 一条说明），
散开才逐条报"可疑"，并在理由里写明 B5。

### 真实配对（真 `.tzs` ↔ 真 `.42f`）：`form42f_realpair_test.go`

上面那些测试是**合成夹具**与**自投影**（`projectF42ToTzs` 把 `.42f` 原样搬成 tzs 侧形状）：
它们能证明"代码按写下的判据跑"，证明不了"判据碰上真实差异会不会误报"。真实配对是第一张网：

```bash
TT_TZS_REAL_DIR=<设计器导出目录，里面有 <表单名>*.tzs> \
TT_FORM_42F=<编译后的那张 .42f> \
  go test ./internal/dev/tzs -run TestForm42FRealPair -count=1 -v
```

两个变量**任一缺失就 `t.Skipf`** 并写明原因（契约 C7.3），绝不拿合成件顶替。这条测试
**不断言"整体零差异"**（真实配对本来就可能不同步），只断言不变量：两侧字段数都 >0、配对 >0、
`Findings` 每条都带分组 + `colName` + 两侧值 + 为什么、`Diffs()` 与 `Undecided()` 严格互补、
`Consistent()` ⇔ 确定差异为 0（CLI 的 6/0 就建在这条上）、同一输入两次渲染逐字节相同。

**A37/A38 之后它多断言两件事**（断的是**规则的效果**，不是"文件一致"）：**编号确定差异必须 0 条
且带 1 条"恒差 +1"的聚合说明**、**可写性确定差异必须 0 条且那 4 条落在未判定里（带 `required` 字样）**。
规则悄悄变宽（误报回来）或变窄（把事实丢了）都会红。

**第一份真实配对实测（2026-10-17，主机 109 的 `aimm200_wf`）**：

| 轮次 | 差异 | 明细 | 未判定 | 退出码 |
|---|---|---|---|---|
| 改规则**前** | **90** | 存在性 0 / **编号 86** / **可写性 4** / 控件族 0 | 7 | **6** |
| 改规则**后** | **0** | 存在性 0 / 编号 0 / 可写性 0 / 控件族 0 | **11** | **0** |

（两侧各 171 条、配对 93 对、仅 `.42f` 有 78 条、tzs 无 `colName` 71 条；两轮相同。）

那 90 条逐条追下去，两类都是**规则误报**，不是设计器与编译件不同步：

1. **编号 86 条 = 下标基数差 1**。`.42f` 的 `fieldId` 是 **0..170**（0 基）、`.4fd` 的是 **1..171**（1 基），
   把两侧按文档顺序逐行对齐，**171 行每行都恰好差 +1** —— 于是旧规则（裸比两侧 `fieldId`）在真实文件上
   **每一条唯一配对都命中**，它对"是不是另一张表单"毫无分辨力。**已改**（契约 A37）：恒差 ⇒ 一条聚合说明。
2. **可写性 4 条全是同一种形状**：`imaa036` / `imaa037` / `imaa038` / `imac002`，都是 `CheckBox`，
   `.42f` 说 `required=1`、`.4fd` 说 `required="false"`，而**两侧 `notNull` 一致（都 true/1）**。
   唯一配对里 `tzs.notNull=true 且 required=false` 的**恰好就是这 4 条**（其余 16 条 `notNull=true` 的
   `required` 两侧都是 true）→ 高度像"编译器把 NOT NULL 列归一成了必填"，而不是设计要求变了。
   **已改**（契约 A38）：跨属性组合进未判定，措辞"疑似"，**不计入确定差异**。
   一份快照证不满（也可能真是导出后又在设计器里改了必填），所以这里永远只是**疑似**。

注意"确定差异从 90 降到 0"**不是成绩**，而是把事实换了个位置：现在报告里仍然是
`1 条【说明】（恒差 +1，附样例 colName）` + `11 条未判定（7 条重名 + 4 条可写性）`。
断言与 `--json` 都看得见它们 —— 这正是"改到不报就完事"与"降级但保真"的分界。

所以这张网的用处是：**规则改过之后，拿它看"误报量有没有变"**；它拦的是"判据悄悄变宽/变窄"，
不是"两个文件必须一样"。


## 引擎侧的契约要点（调用方必须知道的）


以下都在引擎源码里，Go 侧只是转发。改这条链或写调用方时要知道：

| 要点 | 位置 | 内容 |
|---|---|---|
| **`out` 闸门** | `Fns/Session.cs` 的 `CheckOutPath` | 拒绝两种 `out`：指向**任何一个已打开的包**（不只是当前这个 —— `save --form A --out <B 的路径>` 会毁掉 B）、落在**工作区之外**（现在写会成功，但那个包之后打不开：设计器在**加载**时才查工作区）。两条都是参数错（退出码 2），带 `reason` 供自纠 |
| **`save` 的返回** | 同上 | 给刚写出字节的 `sha256` 与 `key`，加一个 `written`。**dry-run 下 `written:false` 而 `sha256` 是"本该写进去的那份"的摘要** —— 这两件事必须一起读 |
| **"值与当前相同"是成功码** | `client.go` 的 `CodeNoOp` / `IsSuccessCode` | 它出现在**成功帧**里（`ok:true` + 标记），退 0，不退 1 |
| **`validate` 是基线相对的** | `Fns/Validate.cs` | 返回 `baseline` / `after` / `newErrors` / `newWarnings` / `elapsedMs`。第一次调用时那次运行**本身就是基线**，所以增量按构造为空 |
| **`reload` 的三态** | `Fns/Session.cs` | `baseline`：`kept`（盘上字节与打开时逐字节相同，基线保留）/ `dropped`（测的是另一份字节，丢弃）/ `none`（没跑过 validate）。`fileChanged` 也是三态 —— **`null` 表示"无法证明"**（打开那次算摘要失败），不是 false。文件字节变了会明确警告"你之前的判断是基于旧字节的" |
| **`describe_kind` 支持 `layout`** | `Fns/Read.cs` | 除了七种节点类型，还接受 `layout`，每条返回 `{name, type, values, initial}` —— **写之前就问得到"这个属性收什么值"** |
| **`list_packages`** | `Fns/Read.cs` | 只列 `.tzs` / `.tzv`（表单侧的两种扩展名；代码包归另一条线）。它不打开包，程序名从文件名推 |
| **`dry_run` 不是靠撤销栈** | `DryRun.cs` | 撤销栈不是模型全部状态，逐字节回不去。实际做法是渲染临时包 → 跑 → 重读，`reverted.mode` 给回滚结论（`none` 表示这个动词的副作用只有文件） |
| **`op` / `list_ops`** | `OpLog.cs` | 幂等操作日志（"超时之后那次写到底进去没有"的机械答案）。日志**只在进程内**、不落盘 |
| **`field_add` 的返回** | `Fns/Session.cs` | 给 `added`（每个新字段带它的表/列绑定，缺失本身也是信息）、`validate`、`baselineCached`，存了包时另给 `saved` |
| **同一程序的第二个包打不开** | `TzpManager`（设计器侧） | `open` 的 key 是 `程序名\|Form`，**不含路径**；新包与源包同名必须先 `close` 再 `open`（`E_KEY_IN_USE`，退 4）。**别读 `TzpManager.Current`**，一律按 key 寻址 |
| **无界面驱动卡住 90 秒** | 设计器侧模态框 | 某些操作会弹**没有消息泵的模态框**（如缺基础资料、只拷 `mta/` 的工作区）。看门狗跑不掉这类——只能整份工作区重试 |

## 退出码

```
0 成功 / 1 引擎内部错 / 2 参数或环境错 / 4 设计器拒绝 / 5 传输或环境失败
```

**没有 3**（3 是 `.tzc` 那条线的"校验失败"）。映射规则统一在 `ExitCode`：
调用出错用它自己的退出码（用法错 2、传输错 5）；**没有应答按传输失败算**（不静默退 0）；
帧成功退 0；否则用帧里错误的退出码。

## 判据

```bash
go test ./internal/dev/tzs -count=1        # 本包测试量最大（约 5.7k 行）
go test ./internal/dev/tzs -run "TestCheckForm42F|TestParseTzsForm4FD|TestReadTzsFormPackage" -count=1 -v
                                           # 静态校验（form42f_check.go）：**不需要**引擎
                                           # 真样本那条走 TT_FORM_SAMPLE_DIR（缺样本 t.Skip 并写明原因）
TT_TZS_REAL_DIR=D:\...\35 TT_FORM_42F=%TEMP%\...\aimm200_wf.42f \
  go test ./internal/dev/tzs -run TestForm42FRealPair -count=1 -v
                                           # **真实配对**（真 .tzs ↔ 真 .42f）：断言结构/不变量 +
                                           # A37/A38 的效果（编号/可写性的确定差异为 0，
                                           # 事实落在【说明】与未判定里）；缺变量 t.Skip 并写明原因
go test ./internal/dev/tzs -run TestMiniCorpus -count=1 -v
                                           # 冒烟回归，跑在**仓库自带**的语料上
                                           # （testdata/tzs-mini/ws，3.2 MB）：
                                           # 不需要任何环境变量，只要能构建引擎
TTZS_E2E=1 go test ./internal/cli/dev -run TestE2E   # 需要真引擎（配 TTZS_EXE / TTZS_WS / TTZS_INSTALL）
./tt.exe dev tzs doctor                    # 五个失败面自检，不引导任何东西
TTZS_DEEP=1 go test ./internal/dev/tzs -run TestCorpus -timeout 30m
                                           # 全语料回归（17 分钟；先在副本上跑）
TTZS_FNS=1 TTZS_CORPUS=%TEMP%\ttws go test ./internal/dev/tzs -run TestFnsGate -timeout 30m -v
                                           # 函数面覆盖：每个语料包一个 --stdio 进程，
                                           # 逐个驱动引擎声明的**全部**写函数（见 fns_test.go 顶部）
```

`TestFnsGate` 是自己的开关（不要求 `TTZS_DEEP`）：它问的是"声明出来的每个写函数被驱动过没有"，
与"这一包写回去还对不对"是两张网。**它只管函数面，不管语料形状** —— 语料回归归 `TestCorpus`。

**它今天是全绿的**（2026-09-27，65 个包）。四条判据各自的结论：

  · 判据一/二：0 个 FAIL，36 个写函数每一个都至少成功驱动过一次
  · 判据三：唯一没有正面用例的 `set_cited` 由引擎自己的 `detail.reason = standard_program`
    背书（见 `fnsNoPositiveCase`）
  · 判据四（写完之后 `RoundTrip` 的不动点）：过

**为了走到全绿，改过两处 —— 两处都不是"把判据放宽"，一处是假阳性、一处是判据与它自己的文案矛盾：**

  1. **`set_items` 的靶子只挑非列派生的**（`pickItems`）。列派生元素（`fieldType` 是
     `COLUMN_LIKE` / `TABLE_COLUMN`）的 `items` 是**派生值**：设计器换列时用新列的 `col_attr`
     覆盖它（`SpecFieldNode.cs:389-397`，反编译源码直证），加载时也重算 —— 写进去下次加载就没了。
     **那是忠实复现设计器，不是缺陷**（引擎自己也知道，返回里带 `derivedFromColumn:true`；
     属性可见性按 ComboBox 控件分，不问是否列绑定，`SpecPropertyEditor.xaml.cs:272`）。
     但判据四量的是"产出还是不是不动点"，会把这件不是缺陷的事报成红 —— 实测 aapt110 上
     13 个候选全是列派生的，写 4 个 → stale 从 0 变 4。所以靶子换掉；
     一个包**只有**列派生的候选时**在报告里说出来**（那 24 条 SKIP 的理由就是它），不静默换靶子。
  2. **`requireFixedPoint` 的 stale 比较从 `!=` 改成 `>`**。它的注释一直写着"判据是
     「不比 pristine 差」"，而 `!=` 实现的是"等于"——差的这一半实测会咬人：`wrap` 在 capt111 上
     把 stale 从 3 降到 2（**把一条本来就存在的不一致写好了**），而 `!=` 把"变好"判成了失败。
     兜底是紧挨着它的四个零（产出没有多出/少掉任何 spec 节点与布局路径），所以一条 stale 的减少
     只可能是属性值收敛，不可能是"把带这个属性的东西删掉了"。

     **这条改的是共享实现**（`corpus_test.go`，真语料那几条也走它），所以两边都重跑过：
     真语料 65 个包的 `TestCorpusRoundTrip` 仍全过。

## 改动影响面

| 改什么 | 会波及 |
|---|---|
| 帧编解码 | 收发两侧的容错是**刻意相反**的，改一边要同时确认另一边；`--json` 下"一次调用恰好一帧"是硬约束 |
| `ExitCode` 映射 | 命令层的退出码全靠它，改错会让脚本按错误的码分支 |
| 参数校验的边界 | "本地不拦三处"是有理由的（见上），收紧会让合法调用到不了引擎 |
| 状态文件结构 / 键的归一 | 与 `reap`、`stop`、`doctor` 三处一致；改了会让已有记录失配（并且可能收错进程） |
| 就绪握手的三条数 | 直接决定"冷启动"体验与慢磁盘上的成功率 |
| 依赖面 | 保持窄：新增对命令层的依赖会成环 |
| `form42f_check.go` 的控件名表 / 判定口径 | 直接决定"差异 vs 未判定"的比例与 `formcheck` 的退出码（6）：放宽会造假差异，收紧会把整类字段变成"不判"。**A37（编号基数感知）与 A38（可写性同属性对齐）是这条的两次实测修正**：前者把 86 条同因误报压成 1 条说明，后者把那 4 条跨属性组合降到未判定 —— 改回去会让真实配对的误报量立刻回到 90 |
