# internal/dev/tzs — `.tzs` 引擎客户端

`.tzs` / `.tzv` 表单包的读写，由**设计器自己的引擎**（C# 外部进程 `tzs-server.exe`）执行；
本包是它的 Go 客户端与守护进程管理。

**它只做两件事，都不做业务判断**：

| 文件 | 职责 |
|---|---|
| `client.go` | 一次调用：连 → 发 → 收 → 把结果归类成类型化错误 |
| `server.go` | 守护进程生命周期：起进程 / 就绪握手 / 状态文件 / 停止 / 收孤儿 |

**依赖面刻意窄**：只 import [config](../../config/README.md)（状态文件落点）与
[winproc](../../winproc/README.md)（起 / 判活 / 杀）加标准库。它**不 import
`internal/dev/cli`** —— 那边 import 它，反过来就成环。命令层（动词分发、退出码、文案）住在
[../cli/README.md](../cli/README.md)，本包只提供退出码映射这类纯函数供它调用。

## 三条纪律

**一、管道名问引擎，不自己算、不缓存。**
名字里混了 `TzsCli.Designer.dll` 的 MVID，每次重编都变。自己重算（或跨调用缓存）算错任何一半
都是**静默失败**：客户端连到一个没人监听的管道、判定"没有守护进程"、起一个新的、还是连不上
（新起的那个监听的是另一个名字），最后报出来的是"冷启动未就绪" —— 与真实原因毫无关系。
所以只用引擎的 `--pipe-name` 开关问一次，代价是几十毫秒（这个开关不 Boot）。

**二、工作区绝不留缺省。**
引擎的内置默认工作区是一个**真实客户目录**。留空就等于拿客户的表单当草稿纸，所以工作区解析
不出来时一律拒绝（退出码 2），**绝不拉起守护进程**。

**三、请求一旦上线绝不重试。**
协议没有幂等键，而这些函数都在改设计器内存里的模型；中途失败时重试是在赌"上一次写进去了没有"。
两种失败要分开对待：

| 现象 | 判定 | 含义 |
|---|---|---|
| 先来一帧致命错误（加载超时）然后 EOF | `E_FATAL_LOAD_TIMEOUT` | 确定性的失败，不重试 |
| 一帧都没有的 EOF | `E_SERVER_DIED` | 连接断了；**下一个**命令可以重新拉起守护进程 |

## 帧

**一行 JSON + 一个换行，UTF-8 无 BOM**，两个方向共用同一条规则，但容错面相反：

- **出方向**只发换行，且**拒绝**帧里出现裸的回车/换行。理由不是洁癖：一个裸换行会把一帧劈成
  两帧，对端在下一次请求上读到上一帧的尾巴，之后每一帧都错位一格 —— 症状是"参数明明对，引擎
  却报参数错或未知函数"。我们的帧全部由 JSON 编码器产出（换行必被转义），所以这条闸门只会
  逮住手搓的帧。
- **入方向**容忍行尾的回车与行首的 BOM。这两个容错不是可选项：标准输入输出模式下的日志/诊断
  可能混到同一条流上，而 BOM 是记事本一类工具的默认输出。
- **行长上限 8 MiB**（双向）。**不要用默认 64 KiB 上限的扫描器**：`form_tree` 在大表单上
  一次就几十万字节，那会以"token too long"终止，读起来像表单坏了。

**不是合法帧的三种情况一律归传输失败**（退出码 5），绝不合成一个看起来像业务错误的应答。
而几处**根本到不了引擎**的失败（连不上、本地参数错、manifest 拉不到）会**合成一帧**
（`SyntheticFailure`），形状与引擎帧完全一致 —— 消费方不必分辨是谁发的。

## 参数：manifest 是唯一权威

命令面只接受**一种**参数写法：`--args '<JSON 对象>'` / `--args-file <文件>`。没有
`--<参数> <值>` 那种写法 —— 参数的名字与类型是**运行时**从引擎的 manifest 来的，
照它为每个动词手写一遍就是几十处会跟引擎漂移的代码。

**绝不在 Go 侧抄第二份参数表。** 本包只做三件事：解 manifest、按名字查表、渲染帮助。
本地只做**语法**层校验（未知动词 / 未知参数 / 缺必填 / 类型 / 枚举静态取值 / 数组元素类型），
语义留给引擎。有三处**本地不拦**：

| 参数 | 为什么拦不了 |
|---|---|
| `kind` | 合法集不在 manifest 里（七种） |
| `attr` | 合法集要从**活着的模型**里取 |
| `add_action` 的 `type` | 是每张表单自己的词表 |

拦下来会让一个引擎本会接受的调用**永远到不了引擎**，而越界拦截是无声发生的（写错了不会有
任何测试失败）。引擎拒绝它们的退出码与本地拦下来一模一样，所以放过不会让报错变晚或变差。

**与引擎自带客户端的一处有意差异**：位置参数与未知开关一律**当场报错**，而引擎那个客户端会
"忽略非选项参数"并继续 —— 无声忽略正是要治的病（打错的参数与一次合法调用在结果上无法区分）。

## 守护进程

**就绪握手**：每 250 ms 试连一次，单次连接超时 300 ms，**连得上就算就绪**（不发任何帧），
预算 60 s。为什么连上就算：管道是引导完成**之后**才创建的，且服务端实例只允许一个，
所以"连上"本身就证明了"引导做完且服务端正等在这里"。**Go 侧不该在传输层写死一个业务函数名。**

**不与 [../../cli/debug](../../cli/debug/README.md) 的后台服务复用**：形状相似但三条前提相反
（我们探命名管道且名字要问引擎 / 状态文件按工作区多条 / 失败还要分有没有致命帧）。
相同的只有"起子进程、判活、杀"三件纯进程原语，那部分已经抽在 `internal/winproc`。

**停止与收孤儿**：`stop` 不带参数就可用（按状态文件找本工作区的守护进程）；
`reap` 收"重编引擎之后再也停不掉"的孤儿。**问不到当前管道名时（引擎 exe 没了/坏了）一个都不动** ——
那时没法把孤儿与现役区分开，猜错就是杀掉一个正在被别的客户端使用的守护进程。

## 状态文件 `.tt-tzs.json`

**必须与 `.tt-serve.json` 分开。** 服务那份要求 URL 非空；一旦混进一条没有 URL 的守护进程记录，
`tt serve` 的单实例判断会当场认为状态文件损坏（于是再拉一个服务抢端口），而 `tt serve --stop`
会拿着引擎的进程号去杀 —— 指错人是这类文件最坏的失败方式：它看起来"成功了"。

结构按工作区键控（一个工作区同时只有一个守护进程），**键是小写的工作区原串，刻意不做路径归一**：
小写是引擎自己的口径（它拿小写串去算管道名），不做清理是因为那会**改变身份** ——
`D:\ws` 与 `D:\ws\` 是两个不同的管道名、两个不同的守护进程，归一成一条会互相覆盖，
`reap` 从此看不到其中一个。

## `doctor`：把"为什么用不了"一次答完

这条链上有五个独立的失败面，而它们的**现象几乎一样**（都是"连不上"），照着现象排查会一路走错：

| 失败面 | 表面现象 |
|---|---|
| 引擎 exe 路径不对 | 问不到管道名 |
| 设计器没装/版本不对 | 冷启动未就绪（真正的错误藏在守护进程日志里） |
| 工作区没配/配错 | 没有守护进程在监听（名字按工作区算） |
| 有陈旧构建留下的孤儿 | 一切正常，只是在吃内存 |
| 状态文件损坏 | 已被静默挪走，但用户该知道 |

`doctor` 把它们分开答，每条给出"在哪看到的"和"怎么办"。它不引导任何东西（只跑两个不引导的
开关），所以可以随便跑。

## 引擎侧的契约要点（调用方必须知道的）

以下都在引擎源码里，Go 侧只是转发。改这条链或写调用方时要知道：

| 要点 | 位置 | 内容 |
|---|---|---|
| **`out` 闸门** | `Fns/Session.cs` 的 `CheckOutPath` | 拒绝两种 `out`：指向**任何一个已打开的包**（不只是当前这个 —— `save --form A --out <B 的路径>` 会毁掉 B）、落在**工作区之外**（现在写会成功，但那个包之后打不开：设计器在**加载**时才查工作区）。两条都是参数错（退出码 2），带 `reason` 供自纠 |
| **`save` 的返回** | 同上 | 给刚写出字节的 `sha256` 与 `key`，加一个 `written`。**dry-run 下 `written:false` 而 `sha256` 是"本该写进去的那份"的摘要** —— 这两件事必须一起读 |
| **"值与当前相同"是成功码** | `client.go` 的 `CodeNoOp` / `IsSuccessCode` | 它出现在**成功帧**里（`ok:true` + 标记），退 0，不退 1 |
| **`validate` 是基线相对的** | `Fns/Validate.cs` | 返回 `baseline` / `after` / `newErrors` / `newWarnings` / `elapsedMs`。第一次调用时那次运行**本身就是基线**，所以增量按构造为空 |
| **`reload` 的三态** | `Fns/Session.cs` | `baseline`：`kept`（盘上字节与打开时逐字节相同，基线保留）/ `dropped`（测的是另一份字节，丢弃）/ `none`（没跑过 validate）。`fileChanged` 也是三态 —— **`null` 表示"无法证明"**（打开那次算摘要失败），不是 false。文件字节变了会明确警告"你之前的判断是基于旧字节的" |
| **`describe_kind` 支持 `layout`** | `Fns/Read.cs` | 除了七种节点类型，还接受 `layout`，每条返回 `{name, type, values, initial}` —— **写之前就问得到"这个属性收什么值"** |
| **`list_packages`** | `Fns/Read.cs` | 只列 `.tzs` / `.tzv`（表单侧的两种扩展名；代码包归另一条线）。它不打开包，程序名从文件名推 |
| **`dry_run` 不是靠撤销栈** | `DryRun.cs` | 撤销栈不是模型全部状态，逐字节回不去。实际做法是渲染临时包 → 跑 → 重读，`reverted.mode` 给回滚结论（`none` 表示这个动词的副作用只有文件） |
| **`op` / `list_ops`** | `OpLog.cs` | 幂等操作日志（"超时之后那次写到底进去没有"的机械答案）。日志**只在进程内**、不落盘 |
| **`field_add` 的返回** | `Fns/Session.cs` | 给 `added`（每个新字段带它的表/列绑定，缺失本身也是信息）、`validate`、`baselineCached`，存了包时另给 `saved` |

## 退出码

```
0 成功 / 1 引擎内部错 / 2 参数或环境错 / 4 设计器拒绝 / 5 传输或环境失败
```

**没有 3**（3 是 `.tzc` 那条线的"校验失败"）。映射规则统一在 `ExitCode`：
调用出错用它自己的退出码（用法错 2、传输错 5）；**没有应答按传输失败算**（不静默退 0）；
帧成功退 0；否则用帧里错误的退出码。

## 改动影响面

| 改什么 | 会波及 |
|---|---|
| 帧编解码 | 收发两侧的容错是**刻意相反**的，改一边要同时确认另一边；`--json` 下"一次调用恰好一帧"是硬约束 |
| `ExitCode` 映射 | 命令层的退出码全靠它，改错会让脚本按错误的码分支 |
| 参数校验的边界 | "本地不拦三处"是有理由的（见上），收紧会让合法调用到不了引擎 |
| 状态文件结构 / 键的归一 | 与 `reap`、`stop`、`doctor` 三处一致；改了会让已有记录失配（并且可能收错进程） |
| 就绪握手的三条数 | 直接决定"冷启动"体验与慢磁盘上的成功率 |
| 依赖面 | 保持窄：新增对命令层的依赖会成环 |
