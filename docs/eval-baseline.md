## 为什么要"只拿 SKILL 的干净 agent"

这是 b530001 那个提交的做法（它的正文写着结论）：**派一个只有 SKILL 的执行者去做一件真事，
它做对了、然后报告说 SKILL 自己的示例教了它一个错值**。那次是偶然发现，这次把它变成常规动作。

它测的不是"模型聪不聪明"，而是**文档与工具面有没有把人带沟里**。所以：

- 执行者**只**读 `skills/tt-dev-tzs/SKILL.md`，明令不许读 WIKI / README / engine / internal /
  别的技能。真实执行者手边资料更多，所以这里的失败是**难度的上界**：这里能过，真机上更宽松。
- 执行者拿到的都是"用户会说的话"（"把某个字段的可编辑关掉"），不是工具术语。
- 不许它改语料：每个任务一份**全新的工作区副本**，写出来的包只落在副本里。

## 装置

每个任务一份全新副本，互不干扰，可以并行：

```
%TEMP%\ttrun\<任务>\ws\        ← hengshuo\prd 的完整副本（485 项 / 130M）
%TEMP%\ttrun\<任务>\config.json ← 该副本的工作区 + 指到 engine/out 的 serverExe
%TEMP%\ttrun\<任务>\tt.exe      ← 刚构建的那份（PATH 上没有 tt，避免测到别的二进制）
```

**只拷 `mta/` 不够**：加载会弹一个无消息泵的模态框，然后 90 秒超时（`E_FATAL_LOAD_TIMEOUT`）。
必须整份拷。

调用形状（每个任务的提示词里都给了）：

```bash
TT_CONFIG=<任务目录>/config.json <任务目录>/tt.exe dev tzs <动词> --args '<JSON>' --json
```

### 这次基线挖出来的东西

按"值不值得马上修"排。前两条是**文档在教错的东西**，后几条是缺口。

**F1（回归，我自己引入的）—— §8 那张表把 `E_NO_OP` 说成"退 1"。**
E1 照着表读到「`E_NO_OP`（"什么都没改"）也在这里（退 1）」，实测却是 **`ok:true` + 退 0**，
`E_NO_OP` 只是 `result.code`。真相是分两路的：绝大多数动词走**成功帧**（`ok:true`，
`noop:true`，退 0），只有 `set_local_string` / `set_spec_description` 那两个把 NoOp 发成了
**错误帧**（`kind=internal` → 退 1）。我上一轮在表里写了"也在这里"，等于把少数情形说成了
普遍情形 —— 而**表比散文更容易被照抄**。这是这份基线抓到的第一个真缺陷，抓到的是我自己的。

**F2 —— 内联 `--args` 里的反斜杠路径会被吃掉一层（4/4 执行者都撞上）。**
SKILL §2/§3 的示例是 `--args '{"path":"D:\\pkg\\aapp320(c).tzs"}'`。在 Git Bash 下实际跑，
反斜杠会少一层，引擎报 `E_BAD_REQUEST` / `invalid character 'U' in string escape code`。
四个执行者**全都**撞上、并且都自己找到了绕过办法（改用正斜杠，或改用 `--args-file`）——
所以它没影响正确性，只花了额外调用（E1 的 27 次里有一部分是它）。
文档只写了"中文/长内容走 `--args-file`"，没说**路径**也容易中招。

**F3 —— SKILL 里没提 `TT_CONFIG`。** §1 只说 `tt config set tzs.workspace` 或 `TZSCLI_WS`。
用另一份配置（便携版、或本次评测这种"不碰用户配置"的跑法）时，入口是 `TT_CONFIG=<配置文件>`，
而 SKILL 一个字没提。

**F4 —— "目标值已经等于目标值"没有定义。** 文档讲清了 `E_NO_OP` 是什么，但没说这种情形下
**该不该照样 `save`**、算成功还是失败、对调用方怎么交代。E1 自己判断成"照存新包 + 如实报告"，
这个判断合理，但那是它自己定的规矩，不是文档定的。

**F5 —— 布局属性的合法集查不到（这是引擎 bug，已定位到行）。**
E2 想要"这个容器能写哪些布局属性"时无处可查，最后是从 `get_component` 回读到一个现成的
`hidden:"false"` 反推出属性名与取值的（而 `get_component` 只列**已经存在**的属性，推不出完整集）。
顺着这条线查下去才看清根因：`describe_kind --args '{"kind":"layout"}'` 回
`E_BAD_PARAM: 不是七种规格节点之一: layout` —— 可函数体**实现了** layout 分支（`Read.cs:458`，
注释还写着"`kind:"layout"` is how the layout side is asked for explicitly"），它死在**参数校验层**：
`Manifest.cs:197` 把 `kind` 声明成 `PType.Kind`，而 `Manifest.cs:536-539` 只认七种。
于是 manifest 里 `set_layout_attr.attr` 的 `from:"layout"` 指向一条**调不通**的发现路径。
已记进 §11.9 第 9 条（引擎批次），SKILL §3 也补了临时可用的两条路。

**F6 —— `<动词> --help` 与 §6 自相矛盾（这是"参数表还没改"的实测代价）。**
E4 的原话：`open --help` 把 `force` 当可用参数列着，描述还写着"占用者只是 Loaded 时强制接管"，
而 §6 说它尚未实现 ——"只有读全文才不会照 help 去试"。这就是 §11.9 第 4 条（从引擎 manifest
删掉 `force`）的代价，现在有了量化：一个干净执行者会在 help 与散文之间撞上一次。

**F7（装置缺陷，不是文档缺陷）—— E1 的任务设计坏了。**
`apcb113_s` 的 `can_edit` 本来就是 `"N"`，所以"设为否"变成了一次 no-op。
下一轮要么换一个当前是 `"Y"` 的字段，要么把任务改成"设为「是」"。
（E1 自己发现并如实报告了这件事 —— 那是执行者靠谱，不是任务设计得对。）

## 已知偏差（读数字之前先读这段）

1. **执行者只读 SKILL**：真机上它还能读 WIKI、README、源码。所以这里的失败是上界。
2. **同一个模型既是文档作者又是被测执行者**：SKILL 里某些说法之所以"够清楚"，可能是因为
   写它的人与读它的模型共享同一套先验。换成别的模型，数字会变。
3. **只有 4 个任务、单次运行**：样本小，不构成统计。它的用途是**找问题**（摩擦报告），
   不是给通过率。三轮都是单次 —— 调用数只能在"同一任务、同一判据"的三轮之间横着看，
   不能当成"文档变好/变坏"的单一指标（第三轮那节给了逐任务读法）。
4. **耗时不可比**：四份副本并行跑，互相争 CPU 与磁盘。第二轮四个都落在 90–110 秒、
   第三轮 71–107 秒，那是并行争用的形状，不是"四个任务难度相同"。
5. **E1 的目标字段在第二轮换过**（F7 的修法）：第二轮起三轮可比，第一轮不可直接比 ——
   那次"设为否"落在了一个本来就是 `N` 的字段上。
6. **每一轮的"修掉"是在那一轮之后做的**：所以第 N 轮的数字对应的是**第 N−1 轮之后**的文档与
   工具面。第四轮量的正是第三轮那 13 条 + 两条引擎改动；它的 13 条摩擦也已修掉。
7. **调用数里混着"文档建议的勤快"**：第四轮有 4 次调用是**新写进文档的步骤**（源包开工前后各
   一次 `sha256sum`、两次 `list_columns` 过滤）。所以逐轮比较要按任务看、并读该轮的"怎么读这组
   数字"——**净下降不等于每一步都更省**。
